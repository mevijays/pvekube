Dex setup

  1. Run Dex somewhere reachable from wherever kubectl runs (it does NOT need to be reachable from the cluster nodes themselves — only token verification happens there, via HTTPS, at API server startup and per-request).
  2. In Dex's config.yaml, add a static client: 
    staticClients:
- id: kubernetes
  name: Kubernetes
  secret: <a-random-secret>   # used by kubectl/oidc-login, never by the API server
  redirectURIs:
  - http://localhost:8000
  3. Configure a connectors: entry for your real identity source (LDAP, SAML, GitHub, Google, etc.) — Dex brokers to it, kube-apiserver only ever talks to Dex.
  4. Below: Issuer URL = Dex's own issuer: value exactly (scheme + trailing slash must match). Client ID = kubernetes (the static client id above).
  5. CA certificate: only needed if Dex's TLS cert isn't from a publicly-trusted CA.

GitHub setup

GitHub doesn't speak OIDC in a way kube-apiserver's OIDC plugin can consume directly — the standard pattern is running Dex as a broker with GitHub as its connector.

  1. GitHub → Settings → Developer settings → OAuth Apps → New OAuth App. Note the Client ID and generate a Client Secret.
  2. In Dex's config.yaml: 
    connectors:
- type: github
  id: github
  config:
    clientID: <from GitHub>
    clientSecret: <from GitHub>
    redirectURI: https://dex.yourdomain.com/callback
    orgs:
    - name: your-github-org
    The orgs:/team mapping is what populates the groups claim.
  3. Add the same staticClients block shown under Dex above.
  4. Below: point Issuer URL/Client ID at Dex, not at GitHub directly.

Azure Entra ID (Azure AD) setup

Entra ID is a real OIDC issuer — no broker needed.

  1. Azure Portal → Entra ID → App registrations → New registration. Note the Application (client) ID and Directory (tenant) ID.
  2. Below: Issuer URL = https://login.microsoftonline.com/<tenant-id>/v2.0. Client ID = the Application (client) ID.
  3. App registration → Token configuration → Add groups claim, or the ID token won't carry one at all. Caveat: Azure AD only inlines up to 200 groups in the token by default (an "overage" claim appears past that) — fine for most homelabs, worth knowing if group counts grow.
  4. Username claim: upn is usually present without extra config; email needs an optional claim added under Token configuration first. Set whichever you actually configured below.
  5. CA certificate: leave blank — Microsoft's cert chains to a public CA.

Generic OIDC setup

Any provider that serves standard OIDC discovery works (Okta, Keycloak, Google, ...): register an application/client with your provider, then below use the issuer URL it gives you (must serve <issuer>/.well-known/openid-configuration) and that client's ID. Ask your provider's admin console what claim it uses for username/groups — defaults here are email/groups, which many but not all providers use.

The exact value your IdP's groups claim returns for this group (no prefix — this app doesn't set oidc-groups-prefix). If set, this group is automatically granted the built-in view ClusterRole cluster-wide (read-only, excludes Secrets) once the cluster comes up — a reasonable default so nobody authenticates successfully and then hits Forbidden on everything. Anything more (e.g. cluster-admin for an ops group) still needs its own ClusterRoleBinding applied by hand after the cluster is up.
