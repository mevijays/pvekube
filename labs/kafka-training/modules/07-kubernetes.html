3. The manifest, piece by piece

Everything lives in labs/kafka/kafka.yaml. Open each section to see why it is there.

Namespace: keep Istio out of Kafka's way
apiVersion: v1
kind: Namespace
metadata:
  name: kafka
  labels:
    istio-injection: disabled

Your cluster runs Istio. Its sidecar proxy would intercept Kafka's TCP traffic and can break Kafka's own protocol handling and add latency. Disabling injection for this namespace keeps broker traffic direct.

Two Services: one for discovery, one for convenience
kind: Service
metadata: { name: kafka-headless }
spec:
  clusterIP: None                 # headless: no virtual IP, DNS returns each pod
  publishNotReadyAddresses: true  # DNS works even before the pod is Ready
  selector: { app: kafka }
  ports: [ { name: client, port: 9092 }, { name: controller, port: 9093 } ]
  • kafka-headless: gives every pod a stable DNS name, kafka-0.kafka-headless.kafka.svc.cluster.local. Brokers must be individually addressable because clients talk to the specific leader of each partition. publishNotReadyAddresses lets brokers find each other while starting up, which the controller quorum needs.
  • kafka (ClusterIP): a normal load-balanced name, good as an initial bootstrap address. After the first contact, clients use the per-pod names.
StatefulSet: identity that survives restarts
kind: StatefulSet
spec:
  serviceName: kafka-headless
  replicas: 3
  podManagementPolicy: Parallel   # start all three together (KRaft needs a quorum to form)
  template:
    spec:
      securityContext: { fsGroup: 1000 }
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector: { matchLabels: { app: kafka } }
              topologyKey: kubernetes.io/hostname
  • A StatefulSet (not a Deployment) because each broker has an identity and its own disk: the pod named kafka-1 is always broker 1 and always reattaches data-kafka-1.
  • Parallel: the default (OrderedReady) would start kafka-0 and wait for it to be Ready, but a lone KRaft node cannot become ready without its quorum peers, so it would deadlock.
  • Anti-affinity: "never put two kafka pods on the same node". With 3 workers this gives exactly one broker per node. Consequence: you cannot scale to 4 brokers without a 4th worker.
  • fsGroup: 1000: the Kafka image runs as user 1000, so the volume must be writable by that group.
The clever startup command: node id and advertised address from the pod name
command: ["/bin/bash", "-c"]
args:
  - |
    export KAFKA_NODE_ID="${HOSTNAME##*-}"        # kafka-2  ->  2
    export KAFKA_ADVERTISED_LISTENERS="PLAINTEXT://${HOSTNAME}.kafka-headless.kafka.svc.cluster.local:9092"
    exec /etc/kafka/docker/run

All three pods share one spec, but each broker needs a unique node.id and must advertise its own address. The pod name (kafka-N) provides both. This is the same trick used by most Kafka-on-Kubernetes manifests.

Kafka configuration through environment variables

The official image turns any env var starting with KAFKA_ into a broker setting: uppercase, dots become underscores. So log.retention.hours becomes KAFKA_LOG_RETENTION_HOURS.

Storage, and the lost+found lesson
volumeMounts:
  - { name: data, mountPath: /var/lib/kafka/data, subPath: kafka }
volumeClaimTemplates:
  - metadata: { name: data }
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: ceph-block
      resources: { requests: { storage: 5Gi } }

volumeClaimTemplates creates one PVC per pod. The pod mounts it at the Kafka data directory.

A bug we hit while building this labA fresh ext4 volume contains a lost+found folder at its root. Kafka treats every folder in its data directory as a topic-partition and crashed: Found directory .../lost+found, 'lost+found' is not in the form of topic-partition. The fix is subPath: kafka, which mounts a clean sub-folder of the volume instead. Remember this symptom: it appears whenever Kafka is pointed at the root of a freshly formatted disk.
Probes, resources and the PodDisruptionBudget
resources:
  requests: { cpu: 250m, memory: 1Gi }
  limits:   { memory: 1536Mi }
readinessProbe: { tcpSocket: { port: 9092 }, initialDelaySeconds: 20 }
livenessProbe:  { tcpSocket: { port: 9092 }, initialDelaySeconds: 60 }
---
kind: PodDisruptionBudget
spec: { minAvailable: 2, selector: { matchLabels: { app: kafka } } }
  • Memory: 512 MB heap plus roughly 1 GB for the JVM overhead and the page cache the pod can use. A limit that is too small gets the pod OOMKilled.
  • PDB minAvailable 2: voluntary disruptions (like kubectl drain) may never take more than one broker at a time. It protects the quorum and the min.insync.replicas=2 rule.
  • Limitation to remember: the readiness probe only checks that port 9092 answers. A restarted broker becomes "Ready" before it has caught up and rejoined the ISR. Module 9 shows how to wait properly.

4. How a client finds the brokers

Kafka clients connect in two steps. Understanding this removes most connection mysteries.

Walkthrough: client connection
Your appin any namespace
→
Bootstrapany one broker
→
Metadatatopic → leader map
→
Leader brokersdirect connections
Why kubectl port-forward does not work for KafkaIn step 3 the broker tells the client its own advertised name, such as kafka-1.kafka-headless.kafka.svc.cluster.local:9092. A laptop cannot resolve that name, and a port-forward only tunnels one pod. The first connection succeeds, then the redirect fails. To reach Kafka from outside you need an extra external listener (NodePort or LoadBalancer) that advertises addresses the outside world can use. That is a separate configuration, intentionally not part of this lab.

So applications inside your cluster use:

bootstrap.servers = kafka-0.kafka-headless.kafka.svc.cluster.local:9092,kafka-1.kafka-headless.kafka.svc.cluster.local:9092,kafka-2.kafka-headless.kafka.svc.cluster.local:9092

From another namespace the full name above is needed. Inside the kafka namespace, kafka-0.kafka-headless:9092 is enough.
