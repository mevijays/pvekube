1. A partition is a folder of segment files

A partition is not one giant file. It is a folder containing segments. Only the newest segment (the active segment) is written; older ones are closed and never change. Each segment is named after the first offset it holds and has three main files:

FileContents
00000000000000000000.logThe actual records, appended in order
00000000000000000000.indexSparse map: offset → byte position in the .log (jump close, then scan)
00000000000000000000.timeindexMap: timestamp → offset (used by "seek to time")

Records are stored in batches (here one batch of 5), exactly as the producer sent them.

2. Retention: how old data is deleted

Kafka deletes whole closed segments, never single records. A closed segment is removed when its newest record is older than the retention time, or when the partition exceeds a size limit. The active segment is never deleted, however old. Play with it:

Experiments
  1. Append 10 records (segments roll as they fill). Advance 3 days: the old closed segments disappear, and Log start offset jumps forward. Those offsets are gone forever; offsets are never reused.
  2. Now append just 1 record, advance 10 days. Nothing is deleted: the active segment is never removed, so old data in a quiet partition lingers.
  3. Tick segment.ms: a segment is now rolled when it gets a day old, so the old records become eligible too. This is why topics with low traffic need a time-based roll.

Your lab sets log.retention.hours=168 (7 days), log.segment.bytes=104857600 (100 MiB) and checks every 60 seconds. You can override retention per topic (module 9).

3. Compaction: keep the latest value per key

Some topics hold state, such as "current address of user 1", where only the newest value per key matters. cleanup.policy=compact keeps the latest record for each key and discards older ones, with no time limit. Offsets stay as they were, so there are gaps.

A tombstone is a record with a key and a null value: it means "this key is deleted". Compaction removes older records, and the tombstone itself disappears after a grace period (delete.retention.ms).

4. Why Kafka is fast

Sequential disk writes

Records are only appended, never updated in place. Sequential writes on disk are close to memory speed and far faster than random writes.

The OS page cache

Kafka leaves caching to the operating system. Recent data sits in RAM, so most consumers read straight from memory. This is why broker heap is small (512 MB here) and the container memory limit leaves room for cache.

Zero-copy transfer

To serve a consumer, the kernel sends bytes from page cache straight to the network card without copying through the JVM.

Batching and compression

Producers send batches; brokers store them as-is; consumers fetch batches. Per-record overhead is spread across many records.

Finding a record is quick too: the .index file is searched (binary search) for the nearest earlier offset, then Kafka scans a short distance in the .log.

5. KRaft: who keeps the cluster's brain?

Brokers need to agree on cluster metadata: which topics exist, who leads each partition, which replicas are in sync. Older Kafka used a separate ZooKeeper cluster for this. Modern Kafka (your 4.0) uses KRaft: a few Kafka nodes called controllers keep a replicated metadata log using the Raft consensus algorithm. No extra system to run.

  • One controller is the active leader; the others are hot standbys that hold identical copies.
  • Decisions need a majority (quorum): 2 of 3 controllers, or 3 of 5. If a majority is lost, the metadata log freezes.
  • The metadata lives in an internal topic __cluster_metadata on each controller (you can see the __cluster_metadata-0 folder on your brokers).
  • In your lab, all 3 brokers are also controllers ("combined mode"). Large production clusters usually run 3 separate dedicated controllers.

6. The group coordinator and __consumer_offsets

Each consumer group is managed by one broker, its group coordinator, which tracks members and heartbeats and triggers rebalances. Committed offsets are stored in the internal topic __consumer_offsets (50 partitions by default, RF 3, which is why you saw a long list of __consumer_offsets-N folders on disk). A group's coordinator is simply the leader of the __consumer_offsets partition that the group id hashes to. Your lab's billing group was coordinated by kafka-2.

7. How much disk do I need?

Disk is usually the first thing that runs out. The estimate is simple: write rate × retention time × replication factor, plus headroom (aim to stay under 60 to 70 percent full).
