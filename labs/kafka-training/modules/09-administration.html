Administration and troubleshooting

Running Kafka is mostly watching a handful of numbers, doing a few operations safely, and knowing where to look when something breaks. This module gives you the checklist, the safe procedures, and a symptom-driven troubleshooter.

40 minutescommand builder12-symptom troubleshooter

By the end you can

  • Run a daily health check in under a minute and read the result
  • Restart brokers safely, one at a time, without losing availability
  • Resize disks, add partitions and change retention
  • Diagnose the common failures from the symptom, in a fixed order

2. The one-minute health check

Run this from your Mac. It prints everything in the table above.

alias k='kubectl --context devk8s-admin@devk8s -n kafka'     # same alias as Lab 0

k get pods -o wide
k exec kafka-client -- bash -c '
B=/opt/kafka/bin
echo "== brokers registered";       $B/kafka-broker-api-versions.sh --bootstrap-server $BS 2>/dev/null | grep -E "^kafka" | cut -d" " -f1,3-5
echo "== controller quorum";        $B/kafka-metadata-quorum.sh --bootstrap-server $BS describe --status | grep -E "LeaderId|MaxFollowerLag:"
echo "== under-replicated (want none)"; $B/kafka-topics.sh --bootstrap-server $BS --describe --under-replicated-partitions
echo "== offline (want none)";      $B/kafka-topics.sh --bootstrap-server $BS --describe --unavailable-partitions
echo "== consumer groups";          $B/kafka-consumer-groups.sh --bootstrap-server $BS --list'
for i in 0 1 2; do echo "== disk kafka-$i"; k exec kafka-$i -- df -h /var/lib/kafka/data | tail -1; done

3. Safe operations

Rolling restart (config change, image upgrade, node maintenance)

Kubernetes will happily restart the next broker as soon as the previous one reports Ready. But Ready here only means port 9092 answers, not that the broker has caught up and rejoined the ISR. If you restart the next broker too early, two replicas are missing at once, you drop below min.insync.replicas, and writes fail. The fix is to wait for the cluster to be fully in sync between restarts:

for i in 2 1 0; do
  echo "restarting kafka-$i"
  kubectl --context devk8s-admin@devk8s -n kafka delete pod kafka-$i
  sleep 3
  kubectl --context devk8s-admin@devk8s -n kafka wait --for=condition=Ready pod/kafka-$i --timeout=300s
  # the important part: wait until no partition is under-replicated
  until [ -z "$(kubectl --context devk8s-admin@devk8s -n kafka exec kafka-client -- bash -c \
      '/opt/kafka/bin/kafka-topics.sh --bootstrap-server $BS --describe --under-replicated-partitions 2>/dev/null')" ]; do
    sleep 5
  done
  echo "kafka-$i is fully in sync"
done
# afterwards, put leaders back on their preferred brokers
kubectl --context devk8s-admin@devk8s -n kafka exec kafka-client -- bash -c \
  '/opt/kafka/bin/kafka-leader-election.sh --bootstrap-server $BS --election-type preferred --all-topic-partitions'
Real result on your cluster 
[  0 s] restarting kafka-2
[ 33 s] kafka-2 Ready          [ 36 s] kafka-2 fully in sync again
[ 36 s] restarting kafka-1
[ 65 s] kafka-1 Ready          [ 68 s] kafka-1 fully in sync again
[ 68 s] restarting kafka-0
[105 s] kafka-0 Ready          [109 s] kafka-0 fully in sync again
Successfully completed leader election (PREFERRED) for partitions __consumer_offsets-15, ...
All three brokers restarted one at a time in 109 seconds, so at least 2 of 3 brokers were always up and acks=all writes stayed possible. Each pod took about 30 seconds to become Ready. On this almost empty cluster the ISR was already full the moment each pod was Ready, so the wait loop did not have to poll. With gigabytes per partition, catching up takes minutes, and that is exactly the wait the loop protects. The final command moved leadership back to each partition's preferred broker.
If you changed the manifestWith kubectl apply the StatefulSet restarts pods itself, one at a time, in reverse order, waiting only for Ready. For a production-grade rollout, either use the loop above, or set updateStrategy.rollingUpdate.partition to step through pods manually and check the ISR between steps.

Grow a disk (no downtime)

Your StorageClass ceph-block allows volume expansion. This procedure was not run in the lab (it would permanently change your volumes), but it is the standard one:

for i in 0 1 2; do
  kubectl --context devk8s-admin@devk8s -n kafka patch pvc data-kafka-$i -p '{"spec":{"resources":{"requests":{"storage":"10Gi"}}}}'
done
kubectl --context devk8s-admin@devk8s -n kafka get pvc -w          # wait for CAPACITY 10Gi, ext4 grows online
kubectl --context devk8s-admin@devk8s -n kafka exec kafka-0 -- df -h /var/lib/kafka/data

A StatefulSet's volumeClaimTemplates cannot be edited in place. To keep the YAML in sync, update kafka.yaml, then kubectl delete sts kafka --cascade=orphan and kubectl apply -f kafka.yaml: the pods and volumes keep running.

Change retention for one topic (instant, no restart)

kafka-configs.sh --bootstrap-server $BS --entity-type topics --entity-name orders --alter --add-config retention.ms=86400000

Change a broker-wide default (rolling restart)

Edit the KAFKA_* env var in kafka.yaml, apply, and watch the restart with the safe loop above.

Add partitions

kafka-topics.sh --bootstrap-server $BS --alter --topic orders --partitions 6

Increase only. Keyed topics: existing keys may move to different partitions for new records.

Add brokers or increase replication factor

Kafka does not automatically move existing partitions onto a new broker. You generate a plan with kafka-reassign-partitions.sh --generate, review it, run it with --execute (optionally throttled so it does not starve production traffic), and confirm with --verify. In this lab you cannot add a 4th broker anyway: pod anti-affinity needs a 4th worker node.

5. Troubleshooter

Pick the symptom you see. You get what it usually means, the checks to run in order, and the fix. Rule of thumb: look at Kubernetes first (is everything running?), then at Kafka (is it healthy?), then at the client.

6. Reading broker logs

k logs kafka-0 --tail=100                       # recent
k logs kafka-0 --previous                       # the crashed container's last words
k logs kafka-0 | grep -E "ERROR|FATAL"          # problems
k logs kafka-0 | grep -iE "Shrinking ISR|Expanding ISR"     # replicas leaving and joining the ISR
k logs kafka-0 | grep -iE "GroupCoordinator|rebalance"      # consumer group activity
k logs kafka-0 | grep -iE "LeaderElection|Elected|controller" # leadership changes
k get events --sort-by=.lastTimestamp | tail -20             # Kubernetes view

Turn up logging on a running broker without a restart (example: replica fetching, broker 0):

kafka-configs.sh --bootstrap-server $BS --entity-type broker-loggers --entity-name 0 --alter \
  --add-config kafka.server.ReplicaFetcherThread=DEBUG
kafka-configs.sh --bootstrap-server $BS --entity-type broker-loggers --entity-name 0 --alter \
  --add-config kafka.server.ReplicaFetcherThread=INFO       # turn it back down

7. Backup, disaster recovery and upgrades

Replication is not backup

Three copies protect against a broker or disk failure. They do not protect against someone deleting a topic, a bad producer writing garbage, or losing the whole cluster or site. For that, mirror to a second cluster (MirrorMaker 2) or snapshot the Ceph volumes, and keep important source data elsewhere too.

Upgrades

Upgrade one broker at a time using the safe rolling procedure, read the release notes for protocol or metadata version steps, and test on a copy first. Never upgrade and change configuration in the same step.
