Module 8 of 10 · On your Kubernetes

Hands-on CLI lab

Twelve short labs against your real cluster. Each one has a goal, commands you can copy, the real output we recorded, and what to notice. Do them in order: later labs reuse earlier topics.

45 to 60 minutes12 labsneeds kubectl access to devk8s
Safe to run?Yes, with one note. Everything here is on the dedicated kafka namespace and uses throwaway topics. Labs 8 and 9 deliberately kill broker pods; the cluster recovers by itself. Do not run these against a Kafka that carries real data.
Two kinds of terminal in the pod means: run inside a shell in the kafka-client pod (set up in Lab 0). on your Mac means: run in a normal terminal. Open two terminal windows: one in the pod, one on your Mac.

0Get a shell and check the cluster is healthy

Goal: reach the Kafka tools, and read a healthy cluster so you know what "normal" looks like.

on your Mac

# a short alias so every later command is easy to type
alias k='kubectl --context devk8s-admin@devk8s -n kafka'

k get pods -o wide
k exec -it kafka-client -- bash

in the pod

export PATH=$PATH:/opt/kafka/bin
echo $BS
kafka-broker-api-versions.sh --bootstrap-server $BS | grep -E '^kafka'
kafka-metadata-quorum.sh --bootstrap-server $BS describe --status | head -8
kafka-1.kafka-headless.kafka.svc.cluster.local:9092 (id: 1 rack: null isFenced: false)
kafka-2.kafka-headless.kafka.svc.cluster.local:9092 (id: 2 rack: null isFenced: false)
kafka-0.kafka-headless.kafka.svc.cluster.local:9092 (id: 0 rack: null isFenced: false)

ClusterId:              MkU3OEVBNTcwNTJENDM2Qk

Notice: three brokers listed, isFenced: false (none are shut out), a controller leader exists, MaxFollowerLag: 0. $BS is a ready-made list of all three brokers.

1Create and describe a topic

Goal: create a topic with 3 partitions and 3 copies, and read where everything landed.

in the pod

kafka-topics.sh --bootstrap-server $BS --create --topic training-orders --partitions 3 --replication-factor 3
kafka-topics.sh --bootstrap-server $BS --list
kafka-topics.sh --bootstrap-server $BS --describe --topic training-orders
Created topic training-orders.

Topic: training-orders  PartitionCount: 3  ReplicationFactor: 3  Configs: min.insync.replicas=2,segment.bytes=104857600
  Partition: 0  Leader: 0  Replicas: 0,1,2  Isr: 0,1,2
  Partition: 1  Leader: 1  Replicas: 1,2,0  Isr: 1,2,0
  Partition: 2  Leader: 2  Replicas: 2,0,1  Isr: 2,0,1

Notice: each partition has a different leader (0, 1, 2): load is spread. Isr equals Replicas: healthy. The Configs were inherited from the broker defaults in the manifest.

Two mistakes you will meet

# Replication factor larger than the broker count
kafka-topics.sh --bootstrap-server $BS --create --topic rf4 --partitions 1 --replication-factor 4
InvalidReplicationFactorException: Unable to replicate the partition 4 time(s): The target replication factor of 4
cannot be reached because only 3 broker(s) are registered.
# Producing to a topic that does not exist (auto-create is off). Press Ctrl-C after a few seconds.
echo x | kafka-console-producer.sh --bootstrap-server $BS --topic does-not-exist
WARN ... {does-not-exist=UNKNOWN_TOPIC_OR_PARTITION}      # repeats every second...
TimeoutException: Topic does-not-exist not present in metadata after 60000 ms.

Notice: a typo in a topic name makes a producer hang for 60 seconds then fail. That is the cost of disabling auto-creation, and worth it.

2Produce and consume

Goal: send messages from one terminal and watch them arrive in another.

in the pod Terminal A (consumer, leave it running):

kafka-console-consumer.sh --bootstrap-server $BS --topic training-orders --from-beginning \
  --property print.key=true --property print.partition=true --property print.offset=true

Terminal B (open a second pod shell with k exec -it kafka-client -- bash, then set PATH again):

kafka-console-producer.sh --bootstrap-server $BS --topic training-orders \
  --property parse.key=true --property key.separator=: --producer-property acks=all
# type lines like these, then Ctrl-D:
cust-A:first order
cust-B:second order
cust-A:third order

Notice: the consumer prints each line with Partition:N Offset:N. Both cust-A lines have the same partition and consecutive offsets. Stop the consumer with Ctrl+C.

3Keys decide partitions

Goal: prove that the same key always lands in the same partition, and see that order across partitions is not guaranteed.

in the pod Send 30 records across 6 customers:

for i in $(seq 1 30); do echo "cust-$(echo ABCDEF | cut -c$(( (i-1)%6+1 ))):order-$i"; done | \
  kafka-console-producer.sh --bootstrap-server $BS --topic training-orders \
  --property parse.key=true --property key.separator=: --producer-property acks=all

kafka-get-offsets.sh --bootstrap-server $BS --topic training-orders --time -1
training-orders:0:5
training-orders:1:10
training-orders:2:15

(These numbers are from a clean topic receiving exactly these 30 records; if you did Lab 2 first yours are a few higher.) Now read it back and group by partition:

kafka-console-consumer.sh --bootstrap-server $BS --topic training-orders --from-beginning --timeout-ms 8000 \
  --property print.key=true --property print.partition=true | grep Partition | sort

Notice: cust-B is always in partition 0, cust-D and cust-E always in partition 1, and so on. The partitions hold 5, 10 and 15 records, so unevenly: with only 6 keys, hashing cannot spread them perfectly. Real systems with thousands of keys balance well. This is a good reason not to use very few keys.

4Consumer groups, lag and replay

Goal: read part of a topic as a named group, inspect lag, finish reading, and rewind.

in the pod

# read only 12 records as group "billing"
kafka-console-consumer.sh --bootstrap-server $BS --topic training-orders --group billing --from-beginning --max-messages 12

kafka-consumer-groups.sh --bootstrap-server $BS --list
kafka-consumer-groups.sh --bootstrap-server $BS --describe --group billing
GROUP    TOPIC            PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
billing  training-orders  1          10              10              0
billing  training-orders  0          2               5               3
billing  training-orders  2          0               15              15

Notice: the group read all of partition 1, part of 0 and none of 2. Lag = 18 records still unread. Now finish and check again:

kafka-console-consumer.sh --bootstrap-server $BS --topic training-orders --group billing --timeout-ms 6000
kafka-consumer-groups.sh --bootstrap-server $BS --describe --group billing    # LAG is now 0 everywhere

# preview a rewind (dry-run changes nothing)
kafka-consumer-groups.sh --bootstrap-server $BS --group billing --topic training-orders --reset-offsets --to-earliest --dry-run
GROUP    TOPIC            PARTITION  NEW-OFFSET
billing  training-orders  1          0
billing  training-orders  0          0
billing  training-orders  2          0

To really rewind (the group must have no running consumers), replace --dry-run with --execute, then run the consumer again: you will see everything replayed.

The TimeoutException printed after a consumer stops on --timeout-ms is normal, not a failure.

5Topic configuration

Goal: change retention for one topic without touching the brokers.

in the pod

kafka-configs.sh --bootstrap-server $BS --entity-type topics --entity-name training-orders --describe
kafka-configs.sh --bootstrap-server $BS --entity-type topics --entity-name training-orders --alter --add-config retention.ms=86400000
kafka-configs.sh --bootstrap-server $BS --entity-type topics --entity-name training-orders --describe
# undo it
kafka-configs.sh --bootstrap-server $BS --entity-type topics --entity-name training-orders --alter --delete-config retention.ms
Dynamic configs for topic training-orders are:            # before: nothing overridden
Completed updating config for topic training-orders.
Dynamic configs for topic training-orders are:
  retention.ms=86400000 sensitive=false synonyms={DYNAMIC_TOPIC_CONFIG:retention.ms=86400000}

Notice: the topic now overrides the broker's 7-day default with 1 day. Changes take effect immediately with no restart. Look at the broker defaults too:

kafka-configs.sh --bootstrap-server $BS --entity-type brokers --entity-name 0 --describe --all | grep -E "log.retention.hours|min.insync|default.replication"

6Watch retention delete data

Goal: see old records disappear. We shrink retention to 20 seconds and the segment size by time to 10 seconds so it happens in about two minutes.

in the pod

kafka-topics.sh --bootstrap-server $BS --create --topic ret-test --partitions 1 --replication-factor 3 \
  --config retention.ms=20000 --config segment.ms=10000

for i in 1 2 3 4 5; do echo "msg-$i"; done | kafka-console-producer.sh --bootstrap-server $BS --topic ret-test

kafka-get-offsets.sh --bootstrap-server $BS --topic ret-test --time -2    # earliest
kafka-get-offsets.sh --bootstrap-server $BS --topic ret-test --time -1    # latest
# now wait about 90 seconds and run the same two commands again
before:  earliest ret-test:0:0     latest ret-test:0:5
after:   earliest ret-test:0:5     latest ret-test:0:5        # all five records deleted

Notice: earliest jumped from 0 to 5. The records are gone, but offsets are never reused, so the next record would get offset 5. Optional: on your Mac, k exec kafka-0 -- ls -la /var/lib/kafka/data/ret-test-0 shows .deleted files for a minute before they vanish. Clean up: kafka-topics.sh --bootstrap-server $BS --delete --topic ret-test

7Measure throughput

Goal: get a feel for how fast this small cluster is, and how acks=all with batching behaves.

in the pod

kafka-topics.sh --bootstrap-server $BS --create --topic perf-test --partitions 3 --replication-factor 3

kafka-producer-perf-test.sh --topic perf-test --num-records 200000 --record-size 200 --throughput -1 \
  --producer-props bootstrap.servers=$BS acks=all linger.ms=10

kafka-consumer-perf-test.sh --bootstrap-server $BS --topic perf-test --messages 200000 --group perf
200000 records sent, 38910.5 records/sec (7.42 MB/sec), 1409.83 ms avg latency, 2806.00 ms max latency ...

data.consumed.in.MB  MB.sec   data.consumed.in.nMsg  nMsg.sec
38.1470              30.7885  200000                 161420.5

Notice: about 39,000 records per second written with full replication on a tiny lab cluster, and the consumer read at about 160,000 records per second (reading is cheaper than writing: no replication wait). The high average latency is because the test sends as fast as possible and records queue in the producer. Try again with linger.ms=0 or acks=1 and compare. Clean up: delete perf-test.

8Failure drill 1: kill one broker

Goal: watch Kafka lose a broker and keep working.

in the pod Terminal A: watch the topic, and keep a producer sending in Terminal B if you like.

watch -n 2 "kafka-topics.sh --bootstrap-server $BS --describe --topic training-orders"

on your Mac Terminal C: kill a broker.

k delete pod kafka-2
k get pods -w                    # watch it come back (Ctrl-C to stop)
Partition: 0  Leader: 1  Replicas: 1,2,0  Isr: 1,0      # broker 2 left the ISR
Partition: 1  Leader: 0  Replicas: 2,0,1  Isr: 0,1      # leadership moved 2 -> 0
Partition: 2  Leader: 0  Replicas: 0,1,2  Isr: 0,1
... after the pod restarts and catches up ...
Partition: 0  Leader: 1  Replicas: 1,2,0  Isr: 1,0,2    # Isr is full again

Notice: (1) Isr shrank for a few seconds; (2) leaders moved on their own; (3) producing with acks=all kept working throughout (2 in-sync replicas ≥ min 2); (4) the broker came back with its data and rejoined. Also try: kafka-topics.sh --bootstrap-server $BS --describe --under-replicated-partitions while it is down: it lists exactly the affected partitions.

9Failure drill 2: lose two brokers

Goal: see Kafka refuse writes instead of risking your data, then recover.

on your Mac

k scale sts kafka --replicas=1      # only kafka-0 remains: 2 of 3 brokers down

in the pod (wait about 25 seconds first)

echo x | kafka-console-producer.sh --bootstrap-server kafka-0.kafka-headless.kafka.svc.cluster.local:9092 \
  --topic training-orders --producer-property acks=all
WARN Got error produce response ... Error: NOT_ENOUGH_REPLICAS, retrying (2 attempts left)
WARN ... retrying (1 attempts left)
WARN ... retrying (0 attempts left)
ERROR Error when sending message to topic training-orders ...

on your Mac restore, then confirm nothing was lost:

k scale sts kafka --replicas=3
k rollout status sts/kafka

Notice: only one in-sync replica was left, below min.insync.replicas=2, so the write was refused and the message x was never stored. After scaling back, all earlier data was intact. Re-read training-orders to confirm. Always scale back to 3.

11Add partitions (and see why you cannot remove them)

Goal: scale a topic out, and learn the one-way rule.

in the pod

kafka-topics.sh --bootstrap-server $BS --create --topic perf-test --partitions 3 --replication-factor 3
kafka-topics.sh --bootstrap-server $BS --alter --topic perf-test --partitions 6
kafka-topics.sh --bootstrap-server $BS --describe --topic perf-test
kafka-topics.sh --bootstrap-server $BS --alter --topic perf-test --partitions 3
PartitionCount: 6  ReplicationFactor: 3          # new partitions 3,4,5 got leaders 0,1,2 automatically
...
InvalidPartitionsException: The topic perf-test currently has 6 partition(s); 3 would not be an increase.

Notice: partitions can only increase. And remember module 2: for keyed topics, increasing the count changes where keys land.

12Clean up

in the pod

for t in training-orders perf-test ret-test keytest; do
  kafka-topics.sh --bootstrap-server $BS --delete --topic $t 2>/dev/null
done
kafka-consumer-groups.sh --bootstrap-server $BS --delete --group billing 2>/dev/null
kafka-consumer-groups.sh --bootstrap-server $BS --delete --group perf 2>/dev/null
kafka-topics.sh --bootstrap-server $BS --list           # only __consumer_offsets should remain

Topic deletion frees the disk on all three brokers, usually within a minute.

Stuck?
  • command not found: you forgot export PATH=$PATH:/opt/kafka/bin in this shell.
  • $BS is empty: you are not inside the kafka-client pod.
  • Commands hang then time out: check k get pods. If fewer than 2 brokers are Running, you are in a failure state (see module 9).
  • A watch screen is stuck on old data: press Ctrl+C.
