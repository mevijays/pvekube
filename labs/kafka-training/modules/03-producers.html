2. Choosing the partition

The partitioner decides which partition gets the record. You met this in module 2:

You provideResult
A keypartition = murmur2(key) % numPartitions. Same key, same partition, ordered.
No keySpread across partitions. Modern clients fill one partition's batch ("sticky") before switching, which gives bigger batches.
An explicit partition numberGoes exactly there. Rarely a good idea.
A custom partitionerYour own class. Useful for special routing.
Gotcha: different libraries hash differently The Java client uses murmur2. Some other libraries default to something else (for example librdkafka uses a CRC32-based consistent_random, and kafka-go's Hash balancer uses FNV-1a). If a Java app and a Go app both write the same key to one topic, they can land in different partitions and break per-key order. Fix: configure the non-Java client for murmur2 compatibility (partitioner=murmur2_random in librdkafka, kafka.Murmur2Balancer in kafka-go).

3. acks: how sure do you want to be?

acks controls when the producer considers a send successful.

acksProducer waits forSpeedCan lose data?
0Nothing. Fire and forget.FastestYes, silently
1The leader wrote it to its logFastYes, if the leader dies before followers copy
all (or -1)Every in-sync replica has it (and at least min.insync.replicas of them)SlowerNo, while one in-sync copy survives

Do not just read it: break it. Pick an acks value, pick when the leader crashes, and send.

Press Send message. Try acks=1 with a crash right after the write, then acks=all with the same crash.
What you should have seen
  • acks=0 or 1 with an early crash: the producer was told "success" but the message exists only on the dead leader. It is gone, and nobody was warned.
  • acks=all with the same crash: no confirmation arrived, so the producer retried against the new leader and the message survived.
The price of acks=all is slightly higher latency (a network hop to the followers). For anything you cannot afford to lose, pay it. Your lab cluster pairs it with min.insync.replicas=2 (module 4).

4. Retries and duplicates

Networks fail. If the producer sent a record but did not see the acknowledgement, it retries. The danger: the first attempt may have succeeded, so the retry writes a duplicate.

The fix is the idempotent producer (enable.idempotence=true, the default in modern clients). The producer gets an id and numbers every record per partition; the broker silently drops any number it has already seen. Retries become safe. It requires acks=all.

AnalogyYou post a numbered form. The office stamps "received #7". If you are unsure and post #7 again, the clerk says "already have #7" and bins the copy.
RememberIdempotence protects against duplicates created by producer retries. It does not protect against your application sending the same business event twice, or a consumer processing twice. That is module 5.

5. Batching and compression

Sending one network request per record would be very slow. Producers group records for the same partition into batches. Two settings control this:

  • linger.ms: how long to wait for more records before sending (default 5 ms in recent clients, older ones 0).
  • batch.size: maximum bytes in a batch (default 16 KB). A full batch is sent immediately.

Simplified model: a batch ships when it is full (about 80 records of 200 bytes in 16 KB) or when linger.ms expires. Raising linger.ms trades a few milliseconds of delay for far fewer requests.

Compression (compression.type = lz4, snappy, zstd or gzip) compresses whole batches. Text-like data (JSON) often shrinks 3 to 5 times, saving network and disk. lz4 or zstd are good defaults.

7. Code: a producer in three languages

Inside Kubernetes, applications use the headless service names. Replace the topic and keys with yours.

Java
Properties p = new Properties();
p.put("bootstrap.servers", "kafka-0.kafka-headless.kafka.svc.cluster.local:9092");
p.put("key.serializer",   "org.apache.kafka.common.serialization.StringSerializer");
p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("acks", "all");
p.put("enable.idempotence", "true");

try (KafkaProducer<String, String> producer = new KafkaProducer<>(p)) {
  producer.send(new ProducerRecord<>("orders", "cust-A", "{\"orderId\":1001}"),
    (meta, err) -> {
      if (err != null) err.printStackTrace();
      else System.out.printf("partition=%d offset=%d%n", meta.partition(), meta.offset());
    });
  producer.flush();
}
Python (confluent-kafka)
from confluent_kafka import Producer

p = Producer({
    "bootstrap.servers": "kafka-0.kafka-headless.kafka.svc.cluster.local:9092",
    "acks": "all",
    "enable.idempotence": True,
    "partitioner": "murmur2_random",   # same hashing as the Java client
})

def done(err, msg):
    print(err or f"partition={msg.partition()} offset={msg.offset()}")

p.produce("orders", key="cust-A", value='{"orderId":1001}', callback=done)
p.flush()
Go (kafka-go)
w := &kafka.Writer{
    Addr:         kafka.TCP("kafka-0.kafka-headless.kafka.svc.cluster.local:9092"),
    Topic:        "orders",
    Balancer:     &kafka.Murmur2Balancer{},   // Java-compatible hashing
    RequiredAcks: kafka.RequireAll,            // acks=all
}
defer w.Close()

err := w.WriteMessages(ctx, kafka.Message{
    Key:   []byte("cust-A"),
    Value: []byte(`{"orderId":1001}`),
})
