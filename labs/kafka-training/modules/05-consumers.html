Consuming data (consumers)

A consumer reads records from topics. Kafka's special trick is the consumer group: many instances of one application share the work automatically, while other applications read the very same data independently.

1. Consumers pull

Kafka does not push messages to consumers. Consumers poll: "give me what you have after offset N". That makes each consumer control its own pace, so a slow consumer never slows a fast one, and a consumer that was down for an hour simply catches up when it returns.

AnalogyA library with a numbered shelf of books (the log). Each reader keeps a bookmark (offset) of where they stopped. Readers read whenever they like, and the library never removes a book because someone read it.

2. Consumer groups: sharing the work

Every consumer sets a group.id. Consumers with the same group id form a consumer group, and Kafka gives each partition to exactly one consumer in the group. Two rules follow:

  • More consumers means more speed, up to the number of partitions.
  • Extra consumers beyond the partition count sit idle (useful as hot standbys, useless for speed).

Different groups are completely independent: Payments, Email and Analytics can each have their own group and each gets every record.

3. Offsets, commits and lag

A consumer's progress is stored by Kafka itself, in an internal topic named __consumer_offsets, as one number per (group, topic, partition): "next offset to read". Saving that number is called committing.

  • Committed offset (CURRENT-OFFSET): where the group will resume after a restart.
  • Log end offset: the newest record in the partition.
  • Lag = log end offset − committed offset: how far behind the group is. It is the single most useful consumer health number.
Real output from your cluster We produced 30 keyed records, let a group named billing read only 12, then described the group: 
$ kafka-consumer-groups.sh --bootstrap-server $BS --describe --group billing

GROUP    TOPIC            PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
billing  training-orders  1          10              10              0
billing  training-orders  0          2               5               3
billing  training-orders  2          0               15              15
Partition 2 had not been read at all (lag 15) and partition 0 was partly read (lag 3). After the group read the rest, every LAG became 0. Notice also that the 12 messages came out as partition 1 first, then partition 0: no ordering across partitions.

Where does a brand-new group start?

If a group has no committed offset (first run, or the data was deleted), auto.offset.reset decides: latest (default: only new records) or earliest (read everything retained). It is only used when there is no committed offset, a classic source of confusion.

Replay

Because records stay, you can move a group's bookmark. With the group stopped: kafka-consumer-groups.sh ... --reset-offsets --to-earliest --execute re-reads everything; --to-datetime or --shift-by go to a time or move relative to now. Bad deploy processed 2 hours of data wrongly? Fix the code, rewind, reprocess.

4. Delivery guarantees: lose it, repeat it, or get it once

The order of two steps, process the record and commit the offset, decides what happens if the consumer crashes in between. Run the same crash (at message 3) under each approach.

Practical adviceMost teams choose at-least-once plus idempotent handlers: for example, an upsert keyed by order id, or "insert if not exists". It is simple, fast and survives every crash. Exactly-once transactions only cover work that stays inside Kafka; a call to an external email service is still at-least-once unless you make it idempotent.

5. Rebalancing, and why it hurts

A rebalance re-deals partitions among group members. It is triggered when a consumer joins, leaves, crashes (no heartbeat), is too slow, or when the topic gains partitions. During a classic rebalance everyone stops reading, so processing pauses.

SettingMeaningTypical value
heartbeat.interval.msHow often the consumer says "I am alive"3000
session.timeout.msNo heartbeat for this long means the consumer is dead and a rebalance starts45000
max.poll.interval.msMax time between poll() calls. If your processing takes longer, you are kicked out of the group.300000
max.poll.recordsRecords per poll. Lower it if each record is slow to process.500
partition.assignment.strategyCooperativeStickyAssignor moves only the partitions that must move, instead of stopping everyonecooperative-sticky
group.instance.id"Static membership": a restarting pod rejoins without triggering a rebalancepod name
Classic mistakeA handler that takes 6 minutes per batch exceeds max.poll.interval.ms, the consumer is evicted, a rebalance starts, the batch is redelivered to someone else, and the cycle repeats. Fix: smaller max.poll.records, faster handlers, or a longer interval.

7. Code: a consumer in three languages

Java
Properties p = new Properties();
p.put("bootstrap.servers", "kafka-0.kafka-headless.kafka.svc.cluster.local:9092");
p.put("group.id", "billing");
p.put("key.deserializer",   "org.apache.kafka.common.serialization.StringDeserializer");
p.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
p.put("auto.offset.reset", "earliest");
p.put("enable.auto.commit", "false");

try (KafkaConsumer<String, String> c = new KafkaConsumer<>(p)) {
  c.subscribe(List.of("orders"));
  while (true) {
    ConsumerRecords<String, String> recs = c.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> r : recs) process(r);  // work first
    c.commitSync();                                            // then commit: at-least-once
  }
}
Python (confluent-kafka)
from confluent_kafka import Consumer

c = Consumer({
    "bootstrap.servers": "kafka-0.kafka-headless.kafka.svc.cluster.local:9092",
    "group.id": "billing",
    "auto.offset.reset": "earliest",
    "enable.auto.commit": False,
})
c.subscribe(["orders"])
try:
    while True:
        msg = c.poll(1.0)
        if msg is None:
            continue
        if msg.error():
            print(msg.error()); continue
        process(msg.key(), msg.value())   # work first
        c.commit(message=msg)             # then commit
finally:
    c.close()
Go (kafka-go)
r := kafka.NewReader(kafka.ReaderConfig{
    Brokers: []string{"kafka-0.kafka-headless.kafka.svc.cluster.local:9092"},
    GroupID: "billing",
    Topic:   "orders",

defer r.Close()

for {
    m, err := r.FetchMessage(ctx)       // does not auto-commit

}
