1. The problem: too many direct connections

Imagine an online shop. When an order is placed, the Orders service must tell Payments, Email and Analytics. Next month a new Fraud service wants to know too. If every service calls every other service directly, each new service means new wiring in several places, and one slow service slows down everyone who calls it.

With a hub, Orders just publishes "an order was placed" and moves on. It does not know or care who listens. Adding the Fraud service later means one new subscriber and zero changes to Orders. That separation is called decoupling, and it is the main reason Kafka exists.

2. So what is Kafka?

Apache Kafka is a distributed event streaming platform. Translated: a cluster of servers that receives streams of events from applications, stores them safely in order, and lets many other applications read them, now or later.

AnalogyThink of a shared notebook where people only ever write at the bottom, never erasing or editing earlier lines. Every line gets a line number. Anyone can read it, each reader keeps their own bookmark, and readers can re-read from any line. Kafka is that notebook, split across many servers so it never gets lost and never runs out of room.

What is an "event"?

An event (Kafka calls it a record or message) is a small fact about something that happened, with a timestamp. It is never edited afterward, because the past does not change.

// An event: "order 1001 was placed by customer cust-A at 10:42:07"
{
  "key":   "cust-A",
  "value": { "orderId": 1001, "item": "keyboard", "amount": 49.90 },
  "timestamp": "2026-11-22T10:42:07Z"
}

3. Kafka vs a traditional message queue

A classic queue (like a post office box) hands each message to one reader and then throws it away. Kafka is different: it is a log. Messages stay for a period you choose (days, weeks, forever), and any number of readers can read them independently.

Traditional queueKafka
After a message is readDeletedStays until retention expires
Several apps need the same dataCopy it into several queuesEach app reads the same log independently
Replay old dataNot possibleYes, rewind your bookmark (offset)
Bad deploy? Reprocess last 2 hoursData is goneReset offset and replay
ScaleLimited by one queueSplit into partitions across many servers
OrderingUsually global, which limits throughputGuaranteed inside one partition

4. Where Kafka is used

Event-driven apps

Microservices react to events like OrderPlaced instead of calling each other.

Activity tracking

Clicks, searches and page views flow to analytics in real time.

Log and metric pipelines

Collect logs from thousands of servers into one durable stream.

Change data capture

Stream every database change to search indexes, caches and warehouses.

IoT and telemetry

Millions of sensor readings per second, buffered safely.

Stream processing

Compute running totals, fraud scores or alerts while data is still flowing.

5. What Kafka promises

Durable

Messages are written to disk and copied to other servers (replication), so they survive crashes. Module 4.

Scalable

Topics are split into partitions spread over brokers. Add partitions and brokers to grow. Module 2.

Ordered where it matters

Messages in one partition are read in exactly the order they were written. Module 3.

Fast

Sequential disk writes and batching give hundreds of thousands of messages per second per broker. Module 6.

6. When Kafka is not the right tool

Be honest about it
  • Simple request/response ("give me this user's profile now"): use an HTTP API.
  • Tiny scale (a few messages a minute between two apps): a simple queue or database table is easier to run.
  • Large files (videos, 500 MB PDFs): store the file in object storage and send only its address through Kafka.
  • You need per-message routing rules or priorities: classic brokers like RabbitMQ are a better fit.
